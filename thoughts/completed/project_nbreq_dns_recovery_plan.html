NBReq DNS Transport Recovery Plan

Incident: 2026-08-26/27  |  Published baseline: nbreq 0.1.1  |  Parent tracker: thoughts/project_nbreq_followup_plan.html  |  Status: D0–D7 accepted; nbreq 0.1.1 published, registry-verified, and live in the ordinary GDS consumer path
Priority: a long-lived native Engine remained unable to resolve names for at least 16 hours after network loss while the configured nameserver, Windows resolver, and fresh NBReq Engines all worked. Treat this as a probable long-lived resolver transport-recovery defect and a candidate 0.1.x repair. Pause F2 implementation and keep its dirty working tree isolated until this incident is reproduced, bounded, and repaired.

Purpose

This tracker preserves the production evidence, separates facts from inference, defines a deterministic synthetic test plus real platform gates, and isolates a minimal release repair from the uncommitted F2 TCP work. It does not assume that the stale component is specifically Windows routing, Mio/AFD registration, the UDP source port, or NBReq state; replacement of the connected UDP socket and its poll registration deliberately covers all of those candidates.

1. Boundary and Safety

  • The immediate subject is the Engine-owned native DNS UDP transport used by native HTTP and, on current main, the public Resolver.
  • DNS answer, NXDOMAIN, NoData, TTL, cache-mode, CNAME, UDP/TCP fallback, cancellation, and HTTP error contracts do not change.
  • Transport/no-answer failures are never promoted into positive or negative DNS cache entries.
  • The first repair is bounded socket/path recovery. Windows network-change notification, dynamic search-suffix changes, and proactive HTTP pool invalidation are later layers unless evidence makes them necessary.
  • Do not disturb the surviving incident process until the optional packet capture is complete or the owner decides its diagnostic value is exhausted.
  • Do not block DNS or alter routing for the whole Ubuntu host. Use a network namespace so the PuTTY/Plink bridge and other host services remain unaffected.
  • Do not mix the repair into the uncommitted F2.1 working tree.

3. Assessment

Strong conclusion: the configured DNS server address was still valid, and resolver state associated with the old Engine differed from fresh working Engines in the same process environment and time window.

The evidence makes stale negative caching and stale nameserver address unlikely. The capture further proves that sampled failed lookups from the old Engine did not enter Windows' monitored packet path, while fresh DNS traffic crossed that path in both directions. The defect therefore precedes wire transmission; it is not merely a lost router reply or unread response. The remaining candidates are concentrated above that boundary:

  • the old connected UDP socket may reject sends immediately after retaining unusable routing/interface state;
  • a persistent socket error may be ignored or converted into repeated DNS failures without socket replacement;
  • the resolver state machine may stop attempting UDP sends while continuing to terminalize queued lookups;
  • stale poll/registration state may contribute to the resolver's failure to return to a send-capable generation;
  • another internal resolver transport state may fail to return to a usable generation.

Replacing both the socket and poll registration is the correct first recovery primitive regardless of which candidate is responsible. Exact v0.1.0 adapter-cycle reproduction remains required before describing the published artifact as conclusively reproduced.

4. Current Implementation Audit

  • System nameservers are discovered during Engine construction and stored in ResolverConfig.
  • The resolver creates one nonblocking Mio UDP socket, binds an unspecified local address, connect()s it to the selected nameserver, and registers it once with the resolver poll owner.
  • Queries retry on that socket according to the configured attempt count and timeout.
  • With multiple configured servers, exhaustion can call advance_nameserver(), which creates and registers a replacement socket before deregistering and dropping the old one.
  • With one configured server, there is no alternate index, so an exhausted no-answer cycle reports DnsFailure::NoNameserver without recreating the same-server socket.
  • Hard UDP send errors currently consume/exhaust retry state. UDP receive errors are ignored by returning from the receive loop. Neither path necessarily rebuilds the transport.
  • Transport/no-answer failure does not intentionally populate the DNS positive/negative cache.
  • Resolver shutdown owns and joins the thread; any replacement must remain on that owner and preserve deterministic teardown.

6. Layered Test Programme

Layer A — Deterministic Rust transport-generation test

Add a private test-only socket factory or equivalent narrow seam while continuing to use real Mio UDP sockets and the real resolver poll loop:

  1. Generation 1 connects to a permanently silent fixture endpoint.
  2. A query exhausts the ordinary retry budget and returns the existing no-answer failure.
  3. The resolver must retire generation 1, deregister it, and construct/register generation 2 for the same logical nameserver.
  4. Generation 2 connects to a responding fixture endpoint.
  5. A subsequent query on the original resolver/Engine succeeds without reconstructing the Engine.

The seam must not mock DNS parsing, retry state, command queues, polling, terminal delivery, cancellation, or shutdown. It exists only to make transport generations deterministic.

Required variants:

  • one and multiple logical nameservers;
  • hard send/receive failure where it can be injected without replacing the whole resolver;
  • several simultaneous pending queries while a generation is retired;
  • positive and negative cache entries survive transport replacement unchanged;
  • transport failures are not cached;
  • repeated failure/replacement/recovery cycles do not grow sockets, poll registrations, transaction IDs, commands, or threads;
  • cancel and shutdown during replacement remain prompt and joined.

Layer B — Ubuntu network namespace

Run a prebuilt test executable inside an isolated network namespace with a veth pair and local DNS fixture. The host bridge remains untouched.

  1. Prove an original Engine resolves while the path is online.
  2. Drop UDP/53 inside the namespace and allow a bounded resolver failure.
  3. Restore traffic and require the original Engine to recover; run a fresh Engine control simultaneously.
  4. Separately remove/recreate the veth route or interface while the original process remains alive, then require recovery.
  5. Repeat one/multiple server cases, outstanding-query and idle-transition cases, cancellation, and shutdown.

Port blocking proves loss/recovery policy. Destroying and recreating the network path is the closer analogue of adapter/DHCP generation change.

Layer C — Windows live adapter gate

  1. Use an external consumer built against exact nbreq 0.1.0 to attempt reproduction.
  2. Start one Engine online and prove resolution.
  3. Disable/disconnect the active adapter long enough for queries to fail.
  4. Reconnect and reacquire DHCP without recreating the Engine.
  5. Prove a fresh Engine works and require the original Engine to recover.
  6. Repeat against the repaired build with one and multiple DNS servers.

This privileged/disruptive gate is deliberate platform evidence, not an ordinary CI test. A dedicated test adapter is preferred; physical cable/Wi-Fi interruption is acceptable when supervised.

Layer D — GDS canary and soak

  • Build an authenticated repaired GDS package without mixing F2.
  • Prove native selection, live polling, authenticated traffic, refresh join, process exit, and ureq rollback.
  • Run a supervised adapter interruption and recovery on the same process.
  • Run an overnight soak after recovery, checking DNS failures, request/POST mapping, callback drain, and normal process shutdown.

7. Recovery Policy

R0 — Minimal correctness repair

  • After a UDP query exhausts the complete configured nameserver retry cycle, retire and recreate the current connected UDP socket and its poll registration, including when only one nameserver exists.
  • The failed query retains its existing terminal and retry budget. Socket recreation prepares subsequent and still-eligible concurrent work; it must not silently double the failed request’s attempts or deadline.
  • Hard UDP send/receive errors poison the current transport generation and trigger bounded replacement rather than leaving the same socket indefinitely. WouldBlock is ordinary drain/backpressure, and Interrupted retries the receive syscall without poisoning.
  • Construct/register the replacement before swapping ownership where practical. If replacement fails, retain a classified bounded failure and retry only under an explicit later trigger; do not leak either registration.
  • Pending transaction IDs and DNS cache data belong to resolver state, not the socket generation. Replacement must preserve their ownership while ensuring packets from a retired generation cannot corrupt later queries.
  • Cancellation, resolver panic fail-all, and shutdown remain authoritative and can interrupt replacement.

R1 — Repeated-generation recovery

  • Only system-discovered resolver configurations are eligible for live rediscovery. Injected fixtures remain deterministic.
  • After a bounded number of failed socket generations, rediscover Windows/Linux nameservers with backoff/rate limiting.
  • Do not silently change the accepted Engine-time search-suffix snapshot in the initial repair. Nameserver rediscovery and suffix policy are separate decisions.
  • Atomically replace the active nameserver list on the resolver owner. Removed servers cannot retain sockets; new servers enter the existing bounded rotation.
  • Expose enough payload-free diagnostics or metrics to distinguish socket replacement, configuration rediscovery, and terminal no-answer without leaking queried hostnames.

R2 — Network-generation integration (later)

  • Evaluate Windows network-change notification as an immediate recovery trigger after R0/R1 correctness is proven.
  • Evaluate a portable internal network-generation signal for proactive idle HTTP connection eviction.
  • Do not make correctness depend solely on notification delivery; bounded failure-triggered recovery remains the fallback.
  • Public API exposure is not required unless operational evidence shows metrics/configuration are insufficient.

10. Open Decisions

IDQuestionCurrent recommendation
DQ-01Does same-server recreation retry the failed query?No for R0. Preserve the configured retry/deadline contract; prepare subsequent and still-eligible concurrent queries to recover. Revisit only if Windows evidence shows one bounded replay is necessary and timeout accounting remains honest.
DQ-02What constitutes a poisoned generation?A complete all-server no-answer cycle or hard UDP send/receive error. WouldBlock is ordinary drain completion and Interrupted retries without poisoning. Malformed/negative DNS replies are protocol/semantic results, not socket poison.
DQ-03When is system configuration rediscovered?Not in R0. For R1, after a bounded number of failed replacement generations with explicit backoff, system-discovered configurations only.
DQ-04Do search suffixes change after rediscovery?No in the initial design. Preserve the accepted Engine-time suffix snapshot until a separate public-contract review.
DQ-05Are recovery counters public?Start with internal/test observability and safe diagnostic text. Add payload-free Engine metrics only if they materially help operators and can be kept backend-honest.
DQ-06Does network change proactively clear HTTP idle connections?Later R2. Ordinary socket errors already destroy used connections; proactive generation-based eviction is useful but not required for the first DNS repair.
