Purpose

This is the working delivery tracker for producing NBReq: a cancellable, concurrent HTTP engine with cheap cloneable Client handles, blocking and callback APIs, no required async runtime, deterministic shutdown, and a backend that can move from libcurl Multi to a Rust-native HTTP/1.1 reactor without changing consumers.

This document describes how the product will be delivered: decision order, implementation slices, test evidence, integration sequence, backend migration, acceptance gates, rollout, and the progress record that future sessions must preserve. Product behaviour belongs in the separate specification.

WP9 pooling and redirects accepted; streaming next: the curl pilot and ureq rollback remain proven and unchanged while the private native backend now owns its reactor, HTTP/1.1 framing, nonblocking UDP/TCP DNS, rustls state, cancellation, joined shutdown, bounded connection acquisition, conservative reuse, and redirect lifecycle on Windows and Ubuntu 20.04/Rust 1.85. WP9.4 now adds incremental TLS upload/download and bounded backpressure. Native remains test-support only; ordinary Engine::new, the accepted GDS package, and backend selection do not change during this work.

1. Current State and Source Map

Starting assets

  • The Delphi TDPHttp implementation supplies a battle-tested slot, callback, progress, timeout, and cancellation model over the GPI socket layer.
  • The Rust GDS implementation already has a portable polling-based socket reactor with a command channel, explicit wakeup, background ownership, and joined shutdown.
  • The WebRPC broker demonstrates a useful single-thread reactor shape, while also confirming that its inline events are internal state transitions rather than arbitrary user callbacks.
  • The current Rust DpHttpClient abstraction isolates most GDS call sites from ureq and includes mocks used by a substantial test body.
  • DPWebRPC provides the first high-value cancellation case: a deliberate long-poll GET currently blocks a ureq caller and complicates shutdown.
  • libcurl Multi supplies the first backend and a mature behavioural reference while the public contract, lifecycle, tests, and GDS integration are established.
Key delivery strategy: curl is dynamically packaged pilot scaffolding, not the public/full-release foundation. It proves the API and solves GDS cancellation first while the existing ureq binding remains selectable for rollback. The Rust-native backend then replaces only the engine beneath a contract and conformance suite that already work.
Three scopes: the core contract defines Engine/Client ownership, cancellation, terminal results, callback safety, timeouts, and shutdown. The curl/GDS milestone implements the smallest production-useful subset of that contract. The native destination completes HTTP/1.1 framing, DNS/TLS ownership, pooling, broader streaming, and full backend parity without moving the public boundary.

2. Delivery Principles

  1. Contract before backend. Write and test terminal-state, cancellation, shutdown, callback, timeout, and error semantics before optimizing transport details.
  2. One ownership boundary. Engine owns resources, lifecycle, worker services, and bulk cancellation. Cloneable Clients submit and individually cancel requests but do not create hidden cancellation domains.
  3. One Engine owner. Engine is not cloneable and is not wrapped in Arc as part of the public ownership model. Explicit shutdown consumes it; other threads signal its owner or use Clients for request work.
  4. Movable owner. Ordinary Engine targets Send without initially promising Sync. Users may build Arc<Mutex<Option<Engine>>> or other shared ownership themselves and own the consequences.
  5. Safe-point dispatch. Backends commit request state and release internal locks before publishing owned callback events. User code never runs on the reactor.
  6. Direct blocking wakeup. Blocking waiters observe committed terminal state directly and never depend on callback-dispatch availability.
  7. Vertical slices. Deliver one complete path at a time: submit → transfer → completion → cancellation → shutdown. Avoid building disconnected layers that cannot be exercised end to end.
  8. Fault-first verification. Every happy-path feature arrives with cancellation, timeout, malformed input, and shutdown cases.
  9. One conformance suite. Curl and native backends run the same public black-box tests. Backend-only tests supplement rather than replace contract tests.
  10. Keep GDS usable. Preserve the existing ureq implementation behind the DpHttpClient seam and keep it configuration/feature selectable throughout curl pilots. Preserve curl as another rollback/reference until the native backend passes parity and canary gates.
  11. No dual-send of real mutations. Differential testing of POST/PUT uses controlled servers and fixtures, never duplicate production requests.
  12. Evidence in this tracker. Record commands, pass counts, fault campaigns, build artifacts, canary observations, and accepted decisions as work progresses.
  13. Small unsafe boundary. Isolate raw backend, OS, TLS, and FFI unsafe code. Require comments identifying ownership and thread invariants.
  14. Observable detachment. Timed shutdown may separate a sealed, self-draining callback domain from a stopped Engine, but it returns a waitable handle. DLL unload is not safe until that handle completes.
  15. Stage the proof. The core lifecycle contract is designed first; the curl/GDS milestone implements the minimum useful slice; the full adversarial and protocol campaign grows with the native destination.
  16. Scope earns expansion. HTTP/2, proxies, decompression, cookies, and elaborate streaming enter only with a named requirement and tests.

8. GDS Integration and Migration

  1. Facade compatibility: audit that all relevant GDS HTTP traffic passes through DpHttpClient, retaining its mocks and current ureq implementation. Add NBReq behind a new binding rather than mixing curl/native concepts into application modules; document any bypassing call site before pilot.
  2. Engine ownership: the GDS HTTP subsystem owns and shuts down one Engine; its components receive cloneable Clients. DPWebRPC retains its own request handle for long-poll cancellation, not a private Client cancellation group.
  3. Long poll first: migrate DPWebRPC's GET because it proves cancellation, rapid restart, handoff, and DLL shutdown. Do not delete the existing workaround until live stop behaviour is measured.
  4. Blocking adapter next: route ordinary JSON/text/form GET/POST calls through NBReq's blocking adapter without changing their business logic.
  5. Feature/config gate: allow ureq and NBReq/curl selection throughout pilot deployment, preferably at client construction/startup. Log only the selected backend and safe diagnostics; keep rollback immediate and unsurprising.
  6. Packaging proof: pin curl and every transitive runtime library beside GDS, load them from a controlled location rather than ambient search paths, and verify Windows 10, Ubuntu 20.04 default Wine, and native Ubuntu 20.04.
  7. Curl DLL lifecycle proof: verify initialization does not perform unsafe loader-lock work, every Engine stops its multi/easy handles and resolver activity, and no per-Engine global cleanup occurs. The supported pilot sequence is controlled load/use/process-exit with both modules pinned; in-process FreeLibrary/reload is explicitly unsupported and must not appear in GDS acceptance language.
  8. Lifecycle campaign: run primary and secondary WebRPC, start/stop/start, settings refresh, watchdog reset, GDS close, and forced network stalls.
  9. Curl canary: deploy narrowly with immediate configuration rollback.
  10. Native switch: later change only backend construction. Repeat the same campaign and retain curl rollback through observation.
Mutation warning: never compare backends by duplicating live WebRPC POSTs or other non-idempotent production calls. Use the test gateway, a recording fake that does not forward, or saved non-secret protocol fixtures.

10. Rollout and Rollback

  1. Local library: run unit, state, adversarial server, and feature-matrix builds.
  2. GDS development: use synthetic/test endpoints; exercise long-poll cancellation and all shutdown paths.
  3. Wine/package verification: build from clean inputs, inspect runtime dependencies, and confirm unload/restart.
  4. Single controlled curl canary: enable NBReq curl for one test/low-risk instance with ureq rollback ready.
  5. Expanded curl observation: monitor cancellation latency, request errors, queue/connection counts, memory, threads, and shutdown duration.
  6. Native test shadow: compare only safe controlled fixtures; do not dual-send production mutations.
  7. Single controlled native canary: select native with curl and ureq rollback retained.
  8. Progressive native rollout: expand only with every release gate linked to evidence.
  9. Default switch: native becomes default; curl remains feature-selectable for an agreed support window.
Rollback: backend selection must occur at Engine construction and must not change the public request contract. Rollback safely shuts down and frees the old Engine before starting its replacement. The transition itself belongs in the lifecycle test matrix.
