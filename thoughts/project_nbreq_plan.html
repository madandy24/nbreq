NBReq Delivery Plan

Product specification: thoughts/nbreq_initial_spec.md  |  First consumer: GDS Rust DPWebRPC  |  Initial plan: 2026-08-15  |  Overall status: WP0 complete; WP1 and private curl proof are next

Purpose

This is the working delivery tracker for producing NBReq: a cancellable, concurrent HTTP engine with cheap cloneable Client handles, blocking and callback APIs, no required async runtime, deterministic shutdown, and a backend that can move from libcurl Multi to a Rust-native HTTP/1.1 reactor without changing consumers.

This document describes how the product will be delivered: decision order, implementation slices, test evidence, integration sequence, backend migration, acceptance gates, rollout, and the progress record that future sessions must preserve. Product behaviour belongs in the separate specification.

M0 passed: the standalone crate, backend-neutral public boundary, private feature seams, trait assertions, and compile-only examples are established. Begin WP1 and the deliberately private curl Multi wakeup/cancellation/DLL experiment. Remaining naming, TLS-root, licensing, numeric latency, and packaging-proof details do not justify another ownership redesign; experimental curl types are not the public API.

1. Current State and Source Map

Starting assets

  • The Delphi TDPHttp implementation supplies a battle-tested slot, callback, progress, timeout, and cancellation model over the GPI socket layer.
  • The Rust GDS implementation already has a portable polling-based socket reactor with a command channel, explicit wakeup, background ownership, and joined shutdown.
  • The WebRPC broker demonstrates a useful single-thread reactor shape, while also confirming that its inline events are internal state transitions rather than arbitrary user callbacks.
  • The current Rust DpHttpClient abstraction isolates most GDS call sites from ureq and includes mocks used by a substantial test body.
  • DPWebRPC provides the first high-value cancellation case: a deliberate long-poll GET currently blocks a ureq caller and complicates shutdown.
  • libcurl Multi supplies the first backend and a mature behavioural reference while the public contract, lifecycle, tests, and GDS integration are established.
Key delivery strategy: curl is dynamically packaged pilot scaffolding, not the public/full-release foundation. It proves the API and solves GDS cancellation first while the existing ureq binding remains selectable for rollback. The Rust-native backend then replaces only the engine beneath a contract and conformance suite that already work.
Three scopes: the core contract defines Engine/Client ownership, cancellation, terminal results, callback safety, timeouts, and shutdown. The curl/GDS milestone implements the smallest production-useful subset of that contract. The native destination completes HTTP/1.1 framing, DNS/TLS ownership, pooling, broader streaming, and full backend parity without moving the public boundary.

2. Delivery Principles

  1. Contract before backend. Write and test terminal-state, cancellation, shutdown, callback, timeout, and error semantics before optimizing transport details.
  2. One ownership boundary. Engine owns resources, lifecycle, worker services, and bulk cancellation. Cloneable Clients submit and individually cancel requests but do not create hidden cancellation domains.
  3. One Engine owner. Engine is not cloneable and is not wrapped in Arc as part of the public ownership model. Explicit shutdown consumes it; other threads signal its owner or use Clients for request work.
  4. Movable owner. Ordinary Engine targets Send without initially promising Sync. Users may build Arc<Mutex<Option<Engine>>> or other shared ownership themselves and own the consequences.
  5. Safe-point dispatch. Backends commit request state and release internal locks before publishing owned callback events. User code never runs on the reactor.
  6. Direct blocking wakeup. Blocking waiters observe committed terminal state directly and never depend on callback-dispatch availability.
  7. Vertical slices. Deliver one complete path at a time: submit → transfer → completion → cancellation → shutdown. Avoid building disconnected layers that cannot be exercised end to end.
  8. Fault-first verification. Every happy-path feature arrives with cancellation, timeout, malformed input, and shutdown cases.
  9. One conformance suite. Curl and native backends run the same public black-box tests. Backend-only tests supplement rather than replace contract tests.
  10. Keep GDS usable. Preserve the existing ureq implementation behind the DpHttpClient seam and keep it configuration/feature selectable throughout curl pilots. Preserve curl as another rollback/reference until the native backend passes parity and canary gates.
  11. No dual-send of real mutations. Differential testing of POST/PUT uses controlled servers and fixtures, never duplicate production requests.
  12. Evidence in this tracker. Record commands, pass counts, fault campaigns, build artifacts, canary observations, and accepted decisions as work progresses.
  13. Small unsafe boundary. Isolate raw backend, OS, TLS, and FFI unsafe code. Require comments identifying ownership and thread invariants.
  14. Observable detachment. Timed shutdown may separate a sealed, self-draining callback domain from a stopped Engine, but it returns a waitable handle. DLL unload is not safe until that handle completes.
  15. Stage the proof. The core lifecycle contract is designed first; the curl/GDS milestone implements the minimum useful slice; the full adversarial and protocol campaign grows with the native destination.
  16. Scope earns expansion. HTTP/2, proxies, decompression, cookies, and elaborate streaming enter only with a named requirement and tests.

4. Implementation Work Packages

WP0 — Resolve product decisions and establish the crate

Complete — 2026-08-16 Established the accepted boundary all later work must preserve.

  • Treat Q-01 through Q-20 as accepted or deliberately deferred per the tracker; do not reopen the ownership contract during scaffolding.
  • Create a standalone-shaped crate with modules for public types, Engine lifecycle, Client command handles, callback dispatch, the internal backend contract, testing support, and feature-gated backends.
  • Freeze the receiver/ownership sketch: client(&self), cancel_all(&self), manual drive(&mut self), and consuming shutdown(self)/shutdown_for(self, duration). Do not make Engine cloneable or prescribe Arc<Engine>.
  • Expose independent Engine::new(config) or equivalent builder construction and Engine-issued client(). Give Client no public constructor; add no hidden or parent/child Engine convenience.
  • Add compile-time trait assertions for ordinary Engine: Send; Client and RequestHandle: Send + Sync; PendingRequest and DetachedCallbacks: at least Send. Do not promise Engine Sync in v1.
  • Require stored spawned callbacks, request data/sources, commands, and waiter state to preserve the Send target. Route any future non-Send manual callbacks through an explicitly local type/mode.
  • Select MSRV, formatting/lint policy, and dependency policy. Use Windows 10 x64, Ubuntu 20.04 default Wine for the Windows build, and native Ubuntu 20.04 x64 as initial targets. Confirm exact MIT/Apache licensing before publication.
  • Build/test Linux artifacts against the Ubuntu 20.04 ABI baseline rather than assuming binaries produced on a newer distribution remain compatible.
  • Write compile-only examples for spawned and manual Engines, cloneable Clients, callback and blocking requests, individual and Engine-wide cancellation, normal/timed shutdown, waiting on detached callbacks, and future FFI use.
  • Forbid backend-specific public types with API review and feature-matrix builds.

Acceptance passed: the dependency-free scaffold crate builds with no backend, curl-only, native-only, both backend features, and all features. Spawned, manual, callback, blocking, cancellation, normal/timed shutdown, detached-callback wait, and future FFI examples compile. Contract tests enforce the positive thread traits and explicit spawned-drive failure; a compile-fail test enforces the initial non-Sync Engine boundary.

WP1 — Implement the request registry and lifecycle model

Ready to begin Delivers backend-independent state transitions.

  • Implement Engine-identified request IDs/generations, terminal-state arbitration, cancellation flags, direct blocking waiters, and owned bounded callback events. Cross-Engine IDs fail closed.
  • Implement Engine states Running → ShuttingDown → Stopped, rejection after shutdown begins, idempotent request cancellation, and one internally idempotent shutdown transition. Public explicit shutdown consumes the unique Engine owner; dropping a Client does not affect Engine lifetime.
  • Make cancel of an already-terminal or stopped same-Engine request an idempotent success; retain a hard wrong-Engine failure. Make spawned drive() and nested/concurrent manual drive fail explicitly.
  • Implement the same state machine in spawned and manual drive modes. The spawned Engine owns its reactor and dispatcher workers; the manual Engine owns no hidden driving thread.
  • Model the spawned callback domain separately: Open → Sealed → Draining → Complete. It owns no Engine/network objects once sealed and may become a self-owned, observable DetachedCallbacks value.
  • Use a deterministic in-memory backend to force completion/cancellation races without network timing.
  • Test callback reentrancy and panic containment after state commit and outside internal locks. Forbid nested manual drive, same-Engine blocking waits, and synchronous Engine join/destruction from a callback.
  • Define command and callback-event backpressure; coalesce progress rather than dropping terminal events. Default to one dispatcher worker; explicit larger pools serialize callbacks per request while allowing different requests to use different workers.

Acceptance: exhaustive state-machine tests demonstrate exactly one terminal outcome, immediate waiter wakeup, safe cancel/complete races, bounded events, per-request callback order, no user callback on the reactor or under internal locks, and a detached callback domain that cannot reach stopped Engine resources.

WP2 — Prove the curl Multi reactor

Open First real transport vertical slice.

  • Own one curl Multi handle and all easy handles on one engine thread.
  • Keep curl Multi inside the spawned reactor so the public Engine remains Send even though the current Rust binding is not. Do not promise manual curl or add an unsafe Send wrapper during the GDS milestone.
  • Submit request specifications through the backend command queue; create curl handles only on the owner thread.
  • Integrate command wakeup with curl waiting. Prefer a documented external wake socket or poll integration over periodic latency.
  • Map curl write/header/progress callbacks into owned per-request state without calling user code.
  • Cancel by removing the transfer on the owner thread; distinguish cancellation from curl failure.
  • Apply the explicit compatibility profile: force HTTP/1.1; disable environment proxies, cookies, automatic decompression, and automatic Expect: 100-continue; implement the agreed redirect/body/auth rules.
  • Treat HTTP 4xx/5xx as completed responses and record the packaged curl version, TLS backend/root strategy, resolver, and relevant runtime capabilities.
  • Build and package a pinned dynamic curl runtime for supported pilot targets. Inventory every transitive DLL/shared-library dependency and control how the application locates it.
  • Prove dependent-DLL resolution before the GDS Rust DLL loads: choose application-directory placement, host preload by absolute path, or another controlled mechanism; reject silent fallback to an unrelated ambient curl.
  • Record curl/TLS/resolver/compression build choices, versions, hashes, licenses/notices, runtime capability output, and the pilot security-update procedure.
  • Use the pinned Rust curl crate's once-only process/module initialization; never perform per-Engine curl_global_cleanup. Keep detached callback domains entirely free of curl/backend objects.
  • Investigate the Windows DLL initializer path against libcurl's loader-lock warning. Prove the exact GDS artifact can initialize, stop all curl/resolver activity, and repeat load/use/unload—or explicitly declare curl-backed DLL unloading unsupported.
  • Prove command wakeup, request cancellation, resolver cleanup, Engine shutdown, and callback-dispatch shutdown using the exact packaged curl build.
  • Measure cancellation latency during connect, slow headers, and stalled body on each supported target; turn the evidence into an explicit gate before WP3 is accepted.

Acceptance: one Engine runs multiple concurrent controlled requests, any request can be cancelled without harming peers, a blocked reactor wakes promptly for commands, normal shutdown joins reactor and callbacks, and timed shutdown stops all network work before returning any detached callback handle.

WP3 — Deliver the callback and blocking APIs over curl

Open Produces the first consumer-usable library.

  • Implement request builders, response values, stable error categories, total/connect/idle timeout options, and redirect policy.
  • Implement bounded owned callback queues, one default spawned off-reactor dispatcher worker, an opt-in larger pool, and manual safe-pass draining, preserving per-request ordering.
  • Make canonical terminal-state commit wake blocking waiters directly before/independently of callback dispatch. A stuck callback worker must not delay PendingRequest::wait() or Engine cancellation of blocking callers.
  • Implement PendingRequest::wait() as returning Completion. Implement execute as sugar mapping Completed to Ok(Response), Failed and Cancelled to distinct errors, and HTTP 4xx/5xx to successful responses.
  • Provide a two-step pending/wait form for individual cancellation from another thread. A waiter-local timeout retains the pending request and does not alter its terminal state.
  • Make wait itself passive. In manual mode another thread must drive the Engine, or single-thread code uses Engine::drive_until(pending); waiting on the active drive/callback stack is forbidden.
  • Implement RequestHandle/RequestId cancellation, Client::cancel(id), Engine::cancel_all(), and deterministic Engine shutdown. Do not add Client::cancel_all().
  • Implement normal shutdown as wait-to-completion and timed shutdown as Complete or CallbacksRemaining(DetachedCallbacks); include zero-duration status and wait/wait-for inspection on the returned handle.
  • Enforce body, header, active-request, queue, and completion-event limits.
  • Document HTTP status versus transport error semantics and cancellation's inability to undo remote effects.

Acceptance: callback and blocking forms derive from the same canonical Completion; a deliberately blocked callback worker cannot delay a blocking waiter; execute mapping and waiter-local timeout semantics pass; Engine cancellation and shutdown immediately release blocked callers; normal shutdown drains callbacks; timed shutdown returns an observable sealed domain when necessary; Clients remain cheap independent command handles; limits and request timeouts behave the same through both APIs.

WP4 — Build the adversarial HTTP test laboratory

Open Built in stages: the lifecycle/cancellation subset gates GDS migration; the full protocol laboratory grows with the native backend and is reused by both.

  • Create a local controlled HTTP/TLS server capable of pausing at DNS substitute, accept, TLS, headers, body, and response completion points.
  • Support byte-by-byte fragmentation, invalid status/headers, conflicting lengths, chunk extensions/trailers, premature EOF, oversized data, redirects, connection reuse, and deliberate stalls.
  • Expose deterministic barriers so tests cancel at named stages rather than relying on sleeps.
  • Add certificate fixtures for valid, wrong-host, expired, and unknown-root cases without checking in secrets.
  • Add property/state tests for terminal arbitration and parser fragmentation; add fuzz targets for native parsing when WP7 begins.
  • Record redacted timing, thread-count, socket-count, and completion evidence.

Acceptance: before GDS migration, deterministic tests cover queue, wakeup, connect, headers/body stalls, cancellation races, callback pressure, and shutdown. Before native release, the complete HTTP/TLS corpus runs unchanged against both backends on Windows and Linux.

WP5 — Integrate the curl-backed client into GDS

Open First production-value milestone.

  • Add an NBReq-backed implementation beside UreqDpHttpClient; preserve current mocks and the rollback path.
  • Give the GDS subsystem explicit ownership of one NBReq Engine and distribute cloneable Clients to callers. Keep blocking convenience for ordinary call sites while giving DPWebRPC ownership of a cancellable long-poll handle.
  • Replace background-detach shutdown workarounds only after NBReq proves bounded stop and request handoff behaviour.
  • Use normal draining shutdown in GDS. Do not use callback detachment on the DLL unload path; GDS callbacks are expected to return promptly and must be joined before unload.
  • Exercise start, stop, rapid restart, primary/secondary endpoints, poll lease/handoff, outbound posts, settings refresh, watchdog reset, and DLL shutdown.
  • Build the GDS DLL/executable with the pinned curl runtime beside it and verify Windows 10, Ubuntu 20.04 default Wine, and native Ubuntu 20.04 packaging.
  • Retain UreqDpHttpClient behind the existing facade and add feature/config selection between ureq and NBReq/curl. Curl remains pilot-only and immediately rollback-capable.

Acceptance: DPWebRPC cancels an in-flight long poll promptly; GDS Engine shutdown cancels all remaining work and joins reactor/dispatch services safely; ordinary GDS HTTP calls retain behaviour; focused Rust, Delphi bridge, live test-gateway, and packaging checks pass.

WP6 — Extract the Rust-native reactor foundation

After curl milestone Begins backend replacement.

  • Extract reusable ideas from Rust DPGPI without coupling NBReq to GDS component types.
  • Implement portable poll registration, notification, timers/deadlines, nonblocking connect, read/write readiness, and slot generations.
  • Keep native manual backend state and all stored inputs/callbacks compatible with moving the uniquely owned Engine between threads; assert Engine remains Send.
  • Keep all sockets and per-connection state on the reactor owner.
  • Implement cancellation and shutdown before adding HTTP.
  • Use a raw TCP echo/script protocol to validate fragmentation, backpressure, error readiness, half-close, and resource cleanup.
  • Run leak, repeated-start/stop, and high-concurrency tests.

Acceptance: the native reactor passes the backend lifecycle contract with scripted TCP transfers and demonstrates prompt cancellation and joined shutdown independently of HTTP/TLS.

WP7 — Implement native HTTP/1.1 framing with `httparse`

After WP6 First cleartext native HTTP slice.

  • Serialize requests and use httparse for response heads and chunk sizes where suitable.
  • Implement no-body, content-length, chunked, and close-delimited response framing.
  • Handle informational responses, malformed/conflicting lengths, premature EOF, trailers, header limits, and arbitrary fragmentation.
  • Start with one request per connection; add safe HTTP/1.1 reuse only after framing tests are complete.
  • Implement buffered bodies and accepted progress/streaming hooks with bounded buffering.
  • Fuzz response parsing and chunk framing; seed the corpus with legacy DPHttp edge cases and adversarial server outputs.

Acceptance: cleartext native requests pass the shared conformance suite and fuzz/property campaigns, including every-byte fragmentation and cancellation at every parse boundary.

WP8 — Add native TLS and DNS

After WP7 Enables production HTTPS.

  • Drive rustls over the reactor using readiness and TLS wants_read/wants_write state.
  • Implement verified trust roots, hostname validation, SNI, and deliberate ALPN. Preserve the current explicit GDS no-verify configuration, determine whether it disables hostname/chain checks, and cover the compatibility mapping with tests.
  • Add a resolver service without blocking the reactor; cache results with expiry and define IPv4/IPv6 selection.
  • Prove request cancellation during resolution and TLS handshake.
  • Prove resolver shutdown is bounded on every release platform or replace it with cancellable/platform/nonblocking resolution.
  • Add Happy Eyeballs after basic correctness if dual-stack connection latency requires it.

Acceptance: valid HTTPS succeeds; wrong host, expired, unknown CA, and interrupted TLS fail correctly; cancellation is prompt; Engine shutdown leaves no resolver or TLS work alive.

WP9 — Add pooling, redirects, streaming, and production limits

After native HTTPS Completes agreed native v1 behaviour.

  • Add bounded per-origin/global connection pooling and idle expiry.
  • Reject reuse after ambiguous framing, premature EOF, unsafe cancellation, or transport failure.
  • Implement the accepted redirect method/body/auth policy identically to curl backend semantics.
  • Complete streaming backpressure, large-body limits, file helpers if required, and progress coalescing.
  • Add fair scheduling across origins and queue-pressure metrics.
  • Benchmark allocation, throughput, connection reuse, cancellation latency, and idle footprint against curl.

Acceptance: the full accepted public contract passes against the native backend under concurrency, pressure, slow consumer, redirect, reuse, and cancellation tests.

WP10 — Establish backend parity and switch the default

After WP9 Removes curl from the default product.

  • Run the complete black-box suite against both backends and classify deliberate differences.
  • Perform differential testing only against controlled endpoints or safe idempotent fixtures.
  • Run Windows, Wine, and Linux soak tests with repeated network interruption and application restart.
  • Run GDS canaries selectable between ureq, curl NBReq, and native NBReq.
  • Switch the crate default only when native meets all gates and rollback remains available.
  • Keep curl as an optional diagnostic/reference backend until at least one stable native release has completed production observation.

Acceptance: GDS changes no code when changing backends; native meets all contract/security/lifecycle gates; observed performance is acceptable; a documented feature rollback remains.

WP11 — Harden, document, and publish

After default switch Produces the reusable public module.

  • Write API guides for blocking programs, callbacks, GUI dispatch, DLL/FFI use, cancellation, shutdown, limits, TLS, and testing.
  • Document MSRV, supported platforms, feature matrix, dependency/licensing inventory, and security reporting.
  • Audit unsafe code, callback panic boundaries, secret redaction, and denial-of-service limits.
  • Provide examples and a small C ABI adapter if accepted.
  • Define semantic-versioning policy and distinguish portable contract from backend extras.
  • Publish only after reproducing builds and release tests from a clean environment.

Acceptance: a new consumer can use NBReq without GDS knowledge; docs state execution and shutdown honestly; release artifacts and tests are reproducible.

8. GDS Integration and Migration

  1. Facade compatibility: audit that all relevant GDS HTTP traffic passes through DpHttpClient, retaining its mocks and current ureq implementation. Add NBReq behind a new binding rather than mixing curl/native concepts into application modules; document any bypassing call site before pilot.
  2. Engine ownership: the GDS HTTP subsystem owns and shuts down one Engine; its components receive cloneable Clients. DPWebRPC retains its own request handle for long-poll cancellation, not a private Client cancellation group.
  3. Long poll first: migrate DPWebRPC's GET because it proves cancellation, rapid restart, handoff, and DLL shutdown. Do not delete the existing workaround until live stop behaviour is measured.
  4. Blocking adapter next: route ordinary JSON/text/form GET/POST calls through NBReq's blocking adapter without changing their business logic.
  5. Feature/config gate: allow ureq and NBReq/curl selection throughout pilot deployment, preferably at client construction/startup. Log only the selected backend and safe diagnostics; keep rollback immediate and unsurprising.
  6. Packaging proof: pin curl and every transitive runtime library beside GDS, load them from a controlled location rather than ambient search paths, and verify Windows 10, Ubuntu 20.04 default Wine, and native Ubuntu 20.04.
  7. Curl DLL lifecycle proof: verify initialization does not perform unsafe loader-lock work, every Engine stops its multi/easy handles and resolver activity, no per-Engine global cleanup occurs, and the supported load/use/unload sequence is reproducible.
  8. Lifecycle campaign: run primary and secondary WebRPC, start/stop/start, settings refresh, watchdog reset, GDS close, and forced network stalls.
  9. Curl canary: deploy narrowly with immediate configuration rollback.
  10. Native switch: later change only backend construction. Repeat the same campaign and retain curl rollback through observation.
Mutation warning: never compare backends by duplicating live WebRPC POSTs or other non-idempotent production calls. Use the test gateway, a recording fake that does not forward, or saved non-secret protocol fixtures.

9. Rust-Native Backend Transition

The native backend begins only after the common lifecycle model and adversarial test laboratory are useful. This prevents the hardest protocol work from simultaneously defining public semantics.

HTTP/1.1 cleartextRequest serialization, httparse response head, body framing.Adversarial corpus, fuzzing, single-connection correctness.

Replacement gate: native becomes default because it satisfies the public contract and operational gates—not merely because it can fetch a page. Curl remains an optional reference until production observation supports removal.

10. Rollout and Rollback

  1. Local library: run unit, state, adversarial server, and feature-matrix builds.
  2. GDS development: use synthetic/test endpoints; exercise long-poll cancellation and all shutdown paths.
  3. Wine/package verification: build from clean inputs, inspect runtime dependencies, and confirm unload/restart.
  4. Single controlled curl canary: enable NBReq curl for one test/low-risk instance with ureq rollback ready.
  5. Expanded curl observation: monitor cancellation latency, request errors, queue/connection counts, memory, threads, and shutdown duration.
  6. Native test shadow: compare only safe controlled fixtures; do not dual-send production mutations.
  7. Single controlled native canary: select native with curl and ureq rollback retained.
  8. Progressive native rollout: expand only with every release gate linked to evidence.
  9. Default switch: native becomes default; curl remains feature-selectable for an agreed support window.
Rollback: backend selection must occur at Engine construction and must not change the public request contract. Rollback safely shuts down and frees the old Engine before starting its replacement. The transition itself belongs in the lifecycle test matrix.
