NBReq Delivery Plan

Product specification: thoughts/nbreq_initial_spec.md  |  First consumer: GDS Rust DPWebRPC  |  Initial plan: 2026-08-15  |  Overall status: WP1 complete; WP2 transport slices proven with remaining environment gates; WP3 consumer API slice in progress

Purpose

This is the working delivery tracker for producing NBReq: a cancellable, concurrent HTTP engine with cheap cloneable Client handles, blocking and callback APIs, no required async runtime, deterministic shutdown, and a backend that can move from libcurl Multi to a Rust-native HTTP/1.1 reactor without changing consumers.

This document describes how the product will be delivered: decision order, implementation slices, test evidence, integration sequence, backend migration, acceptance gates, rollout, and the progress record that future sessions must preserve. Product behaviour belongs in the separate specification.

M1 passed; WP2 in progress: the deterministic lifecycle kernel now drives a private curl Multi backend. Windows proves direct Multi wakeup, concurrent HTTP, owner-thread removal, redirects, generated TLS certificate-policy and handshake-cancellation fixtures, dynamic Schannel packaging, explicit initialization outside the loader path, and process-lifetime DLL use. Native Ubuntu 20.04 passes the same transport/TLS matrix on Rust 1.85 and system libcurl 7.68; its controlled threaded-DNS probe joins cleanly but exposes a curl-pilot latency limitation. The exact Windows package under stock Wine 5 passes transport, cancellation, and explicit no-verify through a tiny audited Rust-runtime compatibility shim; generated custom trust remains a Wine-5 limitation. Prompt connect/DNS teardown is now an accepted curl-only non-claim backed by finite deadlines; the native backend retains the full proof obligation. Minimum Windows 10 and exact GDS packaging remain; experimental curl types are not the public API.

1. Current State and Source Map

Starting assets

  • The Delphi TDPHttp implementation supplies a battle-tested slot, callback, progress, timeout, and cancellation model over the GPI socket layer.
  • The Rust GDS implementation already has a portable polling-based socket reactor with a command channel, explicit wakeup, background ownership, and joined shutdown.
  • The WebRPC broker demonstrates a useful single-thread reactor shape, while also confirming that its inline events are internal state transitions rather than arbitrary user callbacks.
  • The current Rust DpHttpClient abstraction isolates most GDS call sites from ureq and includes mocks used by a substantial test body.
  • DPWebRPC provides the first high-value cancellation case: a deliberate long-poll GET currently blocks a ureq caller and complicates shutdown.
  • libcurl Multi supplies the first backend and a mature behavioural reference while the public contract, lifecycle, tests, and GDS integration are established.
Key delivery strategy: curl is dynamically packaged pilot scaffolding, not the public/full-release foundation. It proves the API and solves GDS cancellation first while the existing ureq binding remains selectable for rollback. The Rust-native backend then replaces only the engine beneath a contract and conformance suite that already work.
Three scopes: the core contract defines Engine/Client ownership, cancellation, terminal results, callback safety, timeouts, and shutdown. The curl/GDS milestone implements the smallest production-useful subset of that contract. The native destination completes HTTP/1.1 framing, DNS/TLS ownership, pooling, broader streaming, and full backend parity without moving the public boundary.

2. Delivery Principles

  1. Contract before backend. Write and test terminal-state, cancellation, shutdown, callback, timeout, and error semantics before optimizing transport details.
  2. One ownership boundary. Engine owns resources, lifecycle, worker services, and bulk cancellation. Cloneable Clients submit and individually cancel requests but do not create hidden cancellation domains.
  3. One Engine owner. Engine is not cloneable and is not wrapped in Arc as part of the public ownership model. Explicit shutdown consumes it; other threads signal its owner or use Clients for request work.
  4. Movable owner. Ordinary Engine targets Send without initially promising Sync. Users may build Arc<Mutex<Option<Engine>>> or other shared ownership themselves and own the consequences.
  5. Safe-point dispatch. Backends commit request state and release internal locks before publishing owned callback events. User code never runs on the reactor.
  6. Direct blocking wakeup. Blocking waiters observe committed terminal state directly and never depend on callback-dispatch availability.
  7. Vertical slices. Deliver one complete path at a time: submit → transfer → completion → cancellation → shutdown. Avoid building disconnected layers that cannot be exercised end to end.
  8. Fault-first verification. Every happy-path feature arrives with cancellation, timeout, malformed input, and shutdown cases.
  9. One conformance suite. Curl and native backends run the same public black-box tests. Backend-only tests supplement rather than replace contract tests.
  10. Keep GDS usable. Preserve the existing ureq implementation behind the DpHttpClient seam and keep it configuration/feature selectable throughout curl pilots. Preserve curl as another rollback/reference until the native backend passes parity and canary gates.
  11. No dual-send of real mutations. Differential testing of POST/PUT uses controlled servers and fixtures, never duplicate production requests.
  12. Evidence in this tracker. Record commands, pass counts, fault campaigns, build artifacts, canary observations, and accepted decisions as work progresses.
  13. Small unsafe boundary. Isolate raw backend, OS, TLS, and FFI unsafe code. Require comments identifying ownership and thread invariants.
  14. Observable detachment. Timed shutdown may separate a sealed, self-draining callback domain from a stopped Engine, but it returns a waitable handle. DLL unload is not safe until that handle completes.
  15. Stage the proof. The core lifecycle contract is designed first; the curl/GDS milestone implements the minimum useful slice; the full adversarial and protocol campaign grows with the native destination.
  16. Scope earns expansion. HTTP/2, proxies, decompression, cookies, and elaborate streaming enter only with a named requirement and tests.

Q-01 Working name and repository location. Use NBReq as a working name in the standalone repository beside GDS. Choose the final public name before publication. Repository accepted; final name open
Q-02 Where callbacks execute. The reactor queues owned events only after committing state and releasing internal locks. Spawned Engines dispatch off-reactor; manual Engines drain inline after a safe drive pass. Accepted in principle
Q-03 Whether cancellation produces a terminal callback. Yes: exactly one Cancelled terminal result for every accepted request. Accepted

Q-10 Spawned and manual execution modes. Support both over the same state machine. Spawned is the convenient default; manual mode progresses and dispatches only when the host drives it, with no nested drive or same-Engine wait/join from callbacks. Accepted in principle
Q-11 Publication and licensing. Aim for a public crates.io release. Choose MIT, Apache-2.0, or dual MIT OR Apache-2.0 after confirming GDS compatibility and dependency notices. Public direction accepted; exact license open

Accepted
Q-14 Default callback dispatcher pool shape. Default to exactly one off-reactor worker. callback_workers(n) explicitly enables a larger pool and cross-request concurrency; per-request ordering remains mandatory. Accepted in principle
Q-15 Terminal callback delivery during shutdown. Publish terminal cancellation for accepted requests and seal the queue. Normal shutdown drains it before returning; timed shutdown transfers the still-draining sealed domain without silently dropping terminal delivery. Accepted in principle
Q-16 Engine ownership and method receivers. Engine is unique, non-cloneable, and not placed in Arc. Client creation and cancel-all take shared access, manual drive takes exclusive access, and normal/timed shutdown consume the Engine. Accepted in principle

4. Implementation Work Packages

WP0 — Resolve product decisions and establish the crate

Complete — 2026-08-16 Established the accepted boundary all later work must preserve.

  • Treat Q-01 through Q-20 as accepted or deliberately deferred per the tracker; do not reopen the ownership contract during scaffolding.
  • Create a standalone-shaped crate with modules for public types, Engine lifecycle, Client command handles, callback dispatch, the internal backend contract, testing support, and feature-gated backends.
  • Freeze the receiver/ownership sketch: client(&self), cancel_all(&self), manual drive(&mut self), and consuming shutdown(self)/shutdown_for(self, duration). Do not make Engine cloneable or prescribe Arc<Engine>.
  • Expose independent Engine::new(config) or equivalent builder construction and Engine-issued client(). Give Client no public constructor; add no hidden or parent/child Engine convenience.
  • Add compile-time trait assertions for ordinary Engine: Send; Client and RequestHandle: Send + Sync; PendingRequest and DetachedCallbacks: at least Send. Do not promise Engine Sync in v1.
  • Require stored spawned callbacks, request data/sources, commands, and waiter state to preserve the Send target. Route any future non-Send manual callbacks through an explicitly local type/mode.
  • Select MSRV, formatting/lint policy, and dependency policy. Use Windows 10 x64, Ubuntu 20.04 default Wine for the Windows build, and native Ubuntu 20.04 x64 as initial targets. Confirm exact MIT/Apache licensing before publication.
  • Build/test Linux artifacts against the Ubuntu 20.04 ABI baseline rather than assuming binaries produced on a newer distribution remain compatible.
  • Write compile-only examples for spawned and manual Engines, cloneable Clients, callback and blocking requests, individual and Engine-wide cancellation, normal/timed shutdown, waiting on detached callbacks, and future FFI use.
  • Forbid backend-specific public types with API review and feature-matrix builds.

Acceptance passed: the dependency-free scaffold crate builds with no backend, curl-only, native-only, both backend features, and all features. Spawned, manual, callback, blocking, cancellation, normal/timed shutdown, detached-callback wait, and future FFI examples compile. Contract tests enforce the positive thread traits and explicit spawned-drive failure; a compile-fail test enforces the initial non-Sync Engine boundary.

WP1 — Implement the request registry and lifecycle model

Complete — 2026-08-16 Delivers backend-independent state transitions.

  • Implement Engine-identified request IDs/generations, terminal-state arbitration, cancellation flags, direct blocking waiters, and owned bounded callback events. Cross-Engine IDs fail closed.
  • Implement Engine states Running → ShuttingDown → Stopped, rejection after shutdown begins, idempotent request cancellation, and one internally idempotent shutdown transition. Public explicit shutdown consumes the unique Engine owner; dropping a Client does not affect Engine lifetime.
  • Make cancel of an already-terminal or stopped same-Engine request an idempotent success; retain a hard wrong-Engine failure. Make spawned drive() and nested/concurrent manual drive fail explicitly.
  • Implement the same state machine in spawned and manual drive modes. The spawned Engine owns its reactor and dispatcher workers; the manual Engine owns no hidden driving thread.
  • Model the spawned callback domain separately: Open → Sealed → Draining → Complete. It owns no Engine/network objects once sealed and may become a self-owned, observable DetachedCallbacks value.
  • Use a deterministic in-memory backend to force completion/cancellation races without network timing.
  • Test callback reentrancy and panic containment after state commit and outside internal locks. Forbid nested manual drive, same-Engine blocking waits, and synchronous Engine join/destruction from a callback.
  • Define command and callback-event backpressure; coalesce progress rather than dropping terminal events. Default to one dispatcher worker; explicit larger pools serialize callbacks per request while allowing different requests to use different workers.

Acceptance passed: deterministic tests cover repeated cancel/complete races, exactly one terminal callback, immediate direct waiters behind a blocked callback worker, Engine-scoped IDs, cancellation barriers, handle/drop behavior, strict concurrent bounded admission through callback return, progress coalescing with terminal priority, per-request serialization and cross-request pool concurrency, callback reentrancy and panic containment, registry-lock exclusion, manual inline dispatch and drive-until, spawned shutdown cancellation, normal drain, timed detachment with actual worker join, stopped captured Clients, and rejection/deferred cleanup of synchronous callback-stack shutdown overlapping an admitted callback activation.

WP2 — Prove the curl Multi reactor

In progress — Windows, Ubuntu-native, and Wine-5 transport slices proven First real transport vertical slice. Evidence: thoughts/wp2_curl_pilot_evidence.md.

  • Own one curl Multi handle and all easy handles on one engine thread.
  • Keep curl Multi inside the spawned reactor so the public Engine remains Send even though the current Rust binding is not. Do not promise manual curl or add an unsafe Send wrapper during the GDS milestone.
  • Submit request specifications through the backend command queue; create curl handles only on the owner thread.
  • Integrate command wakeup with curl waiting. Prefer a documented external wake socket or poll integration over periodic latency.
  • Add the WP2 hardening seam before consumer use: bound every buffered request/response head and body before allocation; contain reactor/factory panics and fail every accepted request; latch external-wakeup failure and combine direct wakeup with a short bounded safety poll; and preserve specific limit/timeout/transport diagnostics.
  • Map curl write/header/progress callbacks into owned per-request state without calling user code.
  • Cancel by removing the transfer on the owner thread; distinguish cancellation from curl failure.
  • Apply the explicit compatibility profile: force HTTP/1.1; disable environment proxies, cookies, automatic decompression, and automatic Expect: 100-continue; implement the agreed redirect/body/auth rules.
  • Treat HTTP 4xx/5xx as completed responses and record the packaged curl version, TLS backend/root strategy, resolver, and relevant runtime capabilities.
  • Build and package a pinned dynamic curl runtime for supported pilot targets. Inventory every transitive DLL/shared-library dependency and control how the application locates it.
  • Prove dependent-DLL resolution before the GDS Rust DLL loads: choose application-directory placement, host preload by absolute path, or another controlled mechanism; reject silent fallback to an unrelated ambient curl.
  • Record curl/TLS/resolver/compression build choices, versions, hashes, licenses/notices, runtime capability output, and the pilot security-update procedure.
  • Use the pinned Rust curl crate's once-only process/module initialization; never perform per-Engine curl_global_cleanup. Keep detached callback domains entirely free of curl/backend objects.
  • Investigate the Windows DLL initializer path against libcurl's loader-lock warning. Prove the exact GDS artifact can initialize, stop all curl/resolver activity, and repeat load/use/unload—or explicitly declare curl-backed DLL unloading unsupported.
  • Prove command wakeup, request cancellation, resolver cleanup, Engine shutdown, and callback-dispatch shutdown using the exact packaged curl build.
  • Implement inactivity as useful-I/O progress measured with a monotonic clock, not curl's whole-second low-speed-rate approximation. If a supported curl target cannot provide honest timing, reject or explicitly narrow that pilot capability without changing the portable contract.
  • Measure cancellation latency during slow headers, stalled body, and TLS handshake on each supported pilot target. Record connect/DNS as bounded curl-only limitations with finite deadlines; retain deterministic connect/resolver cancellation as a native-backend acceptance gate.

Acceptance: one Engine runs multiple concurrent controlled requests, any request can be cancelled without harming peers, a blocked reactor wakes promptly for commands, normal shutdown joins reactor and callbacks, and timed shutdown stops all network work before returning any detached callback handle.

Progress: the exact Windows dynamic package passes concurrent GET/POST/404, informational/final header-budget reset, redirect, timeout, blocked-Multi wakeup, slow-header/body cancellation, Engine shutdown, callback-worker join, and generated TLS certificate-policy and handshake-cancellation tests. Verified local trust succeeds; wrong host, unknown root, and expiry fail at the portable TLS stage; explicit no-verify succeeds without changing the OS trust store or checking in a private key. The hardening seam now bounds request/response bodies and headers before growth, contains reactor/factory panic with fail-all, latches wake failure behind a curl-advertised 50 ms safety poll, implements monotonic useful-I/O inactivity including a 100 ms case, attaches portable timeout/transport/limit detail, suppresses invented custom-method content type, and makes pinned curl initialization fallible. WP3 — Deliver the callback and blocking APIs over curl

Acceptance implementation complete — external review pending Produces the first consumer-usable library.

  • Complete request builders, response values, stable error categories with timeout/transport/limit detail, total/connect/idle timeout options, and redirect policy. Curl error numbers remain private diagnostics.
  • Implement bounded owned callback queues, one default spawned off-reactor dispatcher worker, an opt-in larger pool, and manual safe-pass draining, preserving per-request ordering.
  • Make canonical terminal-state commit wake blocking waiters directly before/independently of callback dispatch. A stuck callback worker must not delay PendingRequest::wait() or Engine cancellation of blocking callers.
  • Implement PendingRequest::wait() as returning Completion. Implement execute as sugar mapping Completed to Ok(Response), Failed and Cancelled to distinct errors, and HTTP 4xx/5xx to successful responses.
  • Provide a two-step pending/wait form for individual cancellation from another thread. A waiter-local timeout retains the pending request and does not alter its terminal state.
  • Make wait itself passive. In manual mode another thread must drive the Engine, or single-thread code uses Engine::drive_until(pending); waiting on the active drive/callback stack is forbidden.
  • Make manual deadline driving genuinely wait or return rather than busy-spin when a command-driven backend has no immediate work. Review reentrant public misuse consistently: document deliberate panics where the return type cannot report misuse, and prefer typed errors for fallible lifecycle operations.
  • Implement RequestHandle/RequestId cancellation, Client::cancel(id), Engine::cancel_all(), and deterministic Engine shutdown. Do not add Client::cancel_all().
  • Implement normal shutdown as wait-to-completion and timed shutdown as Complete or CallbacksRemaining(DetachedCallbacks); include zero-duration status and wait/wait-for inspection on the returned handle.
  • Expose and verify the hardening seam's configurable request/response body, header-byte/header-count, active-request, queue, and completion-event limits through both callback and blocking forms.
  • Keep terminal callback capacity as a named, tested admission invariant rather than an unexplained expect; no reachable queue-pressure path may panic or discard the terminal event.
  • Document the curl pilot's buffered final-header behaviour and avoid claiming portable trailer support until the adversarial/native framing work defines it.
  • Document HTTP status versus transport error semantics and cancellation's inability to undo remote effects.

Acceptance: callback and blocking forms derive from the same canonical Completion; a deliberately blocked callback worker cannot delay a blocking waiter; execute mapping and waiter-local timeout semantics pass; Engine cancellation and shutdown immediately release blocked callers; normal shutdown drains callbacks; timed shutdown returns an observable sealed domain when necessary; Clients remain cheap independent command handles; limits and request timeouts behave the same through both APIs.

Progress: enabling curl-pilot now makes ordinary Engine::new(config) and Engine::builder().build() select the private curl backend; no backend implementation type enters the public contract, and manual construction rejects explicitly. Real local-server tests drive callback and blocking callers through that constructor, prove 404 remains a successful Response, exercise direct timeout/redirect builder policy, confirm late cancellation remains harmless, and prove equivalent response-limit and total-timeout detail through both forms. Engine cancellation and consuming shutdown release a blocked execute() caller as the distinct Cancelled outcome; a waiter-local timeout explicitly retains a live request which can later complete. Request construction now provides all common method builders plus direct connect/inactivity/total timeout, redirect-limit, and TLS-verification setters. Portable HTTP/HTTPS URL, authority, port, method-token, and header validation occurs at build time before admission and is repeated defensively by curl. Manual command-driven driving now sleeps until its deadline or a queue signal rather than spinning. Accepted/inflight, queued-command, and callback-bearing request/event bounds are independently configurable and strictly tested through callback and blocking forms. A terminal callback retains the required permits until return without reducing blocking-only capacity to the callback limit. The terminal callback queue still proves its public admission bound; a defensive invariant-breach path preserves terminal delivery without a library panic or silent discard. The implementation now covers the WP3 acceptance list; external review remains before the work package is marked complete.

8. GDS Integration and Migration

  1. Facade compatibility: audit that all relevant GDS HTTP traffic passes through DpHttpClient, retaining its mocks and current ureq implementation. Add NBReq behind a new binding rather than mixing curl/native concepts into application modules; document any bypassing call site before pilot.
  2. Engine ownership: the GDS HTTP subsystem owns and shuts down one Engine; its components receive cloneable Clients. DPWebRPC retains its own request handle for long-poll cancellation, not a private Client cancellation group.
  3. Long poll first: migrate DPWebRPC's GET because it proves cancellation, rapid restart, handoff, and DLL shutdown. Do not delete the existing workaround until live stop behaviour is measured.
  4. Blocking adapter next: route ordinary JSON/text/form GET/POST calls through NBReq's blocking adapter without changing their business logic.
  5. Feature/config gate: allow ureq and NBReq/curl selection throughout pilot deployment, preferably at client construction/startup. Log only the selected backend and safe diagnostics; keep rollback immediate and unsurprising.
  6. Packaging proof: pin curl and every transitive runtime library beside GDS, load them from a controlled location rather than ambient search paths, and verify Windows 10, Ubuntu 20.04 default Wine, and native Ubuntu 20.04.
  7. Curl DLL lifecycle proof: verify initialization does not perform unsafe loader-lock work, every Engine stops its multi/easy handles and resolver activity, and no per-Engine global cleanup occurs. The supported pilot sequence is controlled load/use/process-exit with both modules pinned; in-process FreeLibrary/reload is explicitly unsupported and must not appear in GDS acceptance language.
  8. Lifecycle campaign: run primary and secondary WebRPC, start/stop/start, settings refresh, watchdog reset, GDS close, and forced network stalls.
  9. Curl canary: deploy narrowly with immediate configuration rollback.
  10. Native switch: later change only backend construction. Repeat the same campaign and retain curl rollback through observation.
Mutation warning: never compare backends by duplicating live WebRPC POSTs or other non-idempotent production calls. Use the test gateway, a recording fake that does not forward, or saved non-secret protocol fixtures.

The native backend begins only after the common lifecycle model and adversarial test laboratory are useful. This prevents the hardest protocol work from simultaneously defining public semantics.

10. Rollout and Rollback

  1. Local library: run unit, state, adversarial server, and feature-matrix builds.
  2. GDS development: use synthetic/test endpoints; exercise long-poll cancellation and all shutdown paths.
  3. Wine/package verification: build from clean inputs, inspect runtime dependencies, and confirm unload/restart.
  4. Single controlled curl canary: enable NBReq curl for one test/low-risk instance with ureq rollback ready.
  5. Expanded curl observation: monitor cancellation latency, request errors, queue/connection counts, memory, threads, and shutdown duration.
  6. Native test shadow: compare only safe controlled fixtures; do not dual-send production mutations.
  7. Single controlled native canary: select native with curl and ureq rollback retained.
  8. Progressive native rollout: expand only with every release gate linked to evidence.
  9. Default switch: native becomes default; curl remains feature-selectable for an agreed support window.
Rollback: backend selection must occur at Engine construction and must not change the public request contract. Rollback safely shuts down and frees the old Engine before starting its replacement. The transition itself belongs in the lifecycle test matrix.

2026-08-15Make normal spawned shutdown wait for the sealed callback domain to drain.This is the least surprising default and suits GDS, whose callbacks are expected to return promptly.
2026-08-15Allow timed shutdown to return an observable DetachedCallbacks domain.Arbitrary user code cannot be interrupted. Once all network services stop and the event queue is sealed, remaining callbacks can finish independently while callers retain status and wait operations.
2026-08-15Keep callback domains independent of Client.Callbacks may capture Client clones, but after Engine shutdown those handles simply return EngineStopped; they do not keep network resources alive.
2026-08-15Do not equate Engine destruction with DLL-unload safety after callback detachment.Detached workers may still execute DLL code or use foreign callback context. Unload is safe only after the callback-domain handle reports complete.
2026-08-15Apply an explicit curl compatibility profile.Backend defaults must not silently define the future native contract. HTTP version, proxies, Expect, redirects, HTTP-status treatment, TLS, and resolver capability are deliberate and recorded.
2026-08-15Use connect timeout, inactivity timeout, and total deadline as the portable initial time model.Inactivity means monotonic elapsed time without useful I/O progress, not curl's average low-speed window. 2026-08-15Keep Engine uniquely owned and out of Arc.Shared Engine ownership would obscure who may drive and destroy it. Shared methods expose commands, manual drive is exclusive, and explicit normal/timed shutdown consumes the owner.
2026-08-15Target ordinary Engine as Send without initially promising Sync.The unique owner may move between threads without becoming cloneable or concurrently driven. Users can add their own Arc<Mutex<Option<Engine>>> ownership and assume its locking/shutdown consequences.
2026-08-15Do not let manual curl determine Engine's thread traits.Spawned curl keeps its non-Send Multi on the reactor. Native manual targets Send; manual curl remains unsupported/thread-bound unless a pinned unsafe-wrapper audit later justifies it.
2026-08-15Default spawned callback dispatch to one worker.This matches GDS/foreign-host expectations and minimizes thread/lock surprises. A larger pool is explicit while retaining per-request ordering.
2026-08-15Wake blocking requests directly from canonical terminal-state commit.Blocking callers must not depend on callback-pool availability. Pending wait returns Completion; execute is only response/error mapping sugar.
2026-08-15Keep waiter-local timeout separate from request timeout.A local wait timeout returns the still-live pending request; only a configured request deadline creates a terminal timeout failure.
2026-08-15Do not perform per-Engine curl global cleanup.The pinned Rust curl layer uses once-only initialization and deliberately avoids global cleanup. Engines own handles and resolver activity, while detached callback domains remain curl-free; DLL safety requires an exact artifact proof.
2026-08-15Use dynamically packaged curl only for pilots.Static curl is unnecessary for the stepping stone. Pin and audit adjacent runtime libraries, retain ureq selection in DpHttpClient, and defer broad/full release until the native backend if desired.
2026-08-15Set initial platform targets to Windows 10 x64, Ubuntu 20.04 default Wine, and native Ubuntu 20.04 x64.These reflect current GDS deployment needs and may vary only when a concrete compatibility problem is recorded.
2026-08-15Preserve the current explicit GDS no-verify mode.Some deployments still require it. Verification remains default; integration must determine and test the legacy hostname/chain semantics.
2026-08-15Aim for a public crates.io release.Exact MIT, Apache-2.0, or dual licensing remains open pending GDS compatibility and dependency-notice review.
2026-08-16Issue Clients only from independently constructed Engines.Engine::new(config) establishes an independent ownership and cancellation domain; engine.client() issues command handles. There is no public Client::new(), hidden Engine, or parent/child Engine relationship.
2026-08-16Make mode misuse and late cancellation boring and explicit.drive() is manual-only and rejects spawned, nested, or concurrent use. Cancelling a terminal same-Engine request is an idempotent success even after stop; a wrong-Engine ID still fails closed.
2026-08-16Accept the conservative redirect table and narrow the pilot contract.The curl/GDS pilot implements buffered bodies and connect/inactivity/total time controls. 2026-08-16Close the architecture contract for WP0.Remaining naming, trust-root, licensing, measured-latency, dependency-inventory, and GDS HTTP-scope work can be resolved without reopening Engine/Client ownership.
2026-08-16Use Rust 2024 edition with MSRV 1.85 for the initial crate.Edition 2024 makes the language baseline explicit while 1.85 is its first supported compiler. GDS currently builds with a newer toolchain; supported-platform artifact tests remain separate from the language MSRV.
2026-08-16Begin with zero runtime dependencies and private empty backend feature seams.The WP0 scaffold proves the public boundary without accidentally blessing curl/native implementation types. Every future dependency requires purpose, platform, license, and runtime-model review.
2026-08-16Keep the crate non-publishable until naming and licensing close.publish = false prevents an accidental crates.io release under a working identity or incomplete grant while leaving the standalone crate structure real.
2026-08-16Separate closed admission from completed shutdown.A teardown error still seals callback admission but retains incomplete backend state for retry. Neither the stopped flag nor a repeated cleanup call may hide an earlier incomplete teardown.
2026-08-16Keep DetachedCallbacks unique and non-cloneable.One observation handle makes final-wait and DLL-unload responsibility obvious, while the sealed callback domain remains self-owned if the handle is dropped.
2026-08-16Quarantine curl pilot compromises behind the private backend boundary.Curl-specific wake fallback, initialization, feature gating, timeout machinery, and process-lifetime module pinning may differ internally. They may not weaken or redefine the public native destination.
2026-08-16Insert a WP2 hardening seam before WP3.Bound buffered data before growth, fail all accepted requests on reactor/factory panic, latch wake failures with a short safety poll, and carry backend-neutral timeout/transport/limit detail. 2026-08-16Commit terminal state synchronously in the backend-independent registry.Cancellation and backend completion race on one canonical state. The winner wakes direct waiters immediately and queues any callback; the reactor is separately awakened to clean backend resources.
2026-08-16Bound admission through terminal callback return.An admission permit moves into terminal callback work and is released after user code returns, guaranteeing bounded terminal delivery. Progress may coalesce or yield its slot; terminal events never do.
2026-08-16Track callback activation across registry unlock and shutdown seal.Fast completion cannot invoke user code while the registry is locked, and shutdown cannot seal before every accepted callback has either been queued or proven unnecessary.
2026-08-16Reject synchronous Engine shutdown on its callback stack and defer cleanup.A callback cannot join itself. The misuse path closes admission, transfers cleanup to a helper, and returns ReentrantOperation; normal callers signal the owner and shut down after unwinding.
